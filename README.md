# CareerSafari

> **帮大学初期的人（大一 / 研一 · 方向未定型）想清楚三件事：该往哪个方向走、现在差什么、接下来两周做什么。**
>
> 每条建议都有依据、能点开核查；不确定的明确说不确定。

## 项目规格（Agent 可执行的完整规格）

### 1. 要做什么

一个本地 Web 应用，两个页面：

**页面一 · 用户画像端** —— 五步向导采集，输出「求职意向定义卡」+「求职与学习建议」

| 步骤 | 采集内容 | 关键约束 |
|---|---|---|
| 1 硬约束 | 专业 / 年级 / 倾向方向 / 期望工作地 / 必须落地的时间点 / 不可接受项 / 实习目标 | 每一项都可选「我不确定」，登记为 `unknown` |
| 2 能力 | 两栏：通用可迁移 ｜ 目标岗位相关 | 每项区分「有证据」与「仅自述」；声称有证据必须写来源，否则自动降级 |
| 3 兴趣 | RIASEC 六型各 3 题共 18 题；MBTI 可选 | MBTI 必须强制展示信度局限 |
| 4 价值观 | 100 分分配到 6 个维度 | 实时显示合计，超额标红 |
| 5 未知项 | 候选清单 + 自定义 | 「我不确定」是合法输出 |

**页面二 · 岗位知识库** —— 三种入口（手动粘贴 / URL 采集 / 文件导入）采集 JD，
LLM 拆解为原子化需求，**人工逐条确认后**入库。

### 2. 五条不可协商的设计原则

**① 原子化判据：拆到「能否被单独验证」为止。**
「熟悉 SQL」不可验证；「能独立编写多表 JOIN 查询」可验证。
这个判据决定匹配能不能做——拿不可验证的条目比对用户自评，比出来的数是假的。

**② evidence_span 回查（生成后校验）。**
每条需求必须附 `evidence_span`（JD 原文**逐字复制**的支撑句）。程序归一化后回到原文
做子串匹配，匹配不上的标记「无原文支撑」并降级为 `team` 置信度 0.3，
**不当作外部证据采信**。全部不通过则整体拒绝入库。

**③ 先约束后偏好。**
采集顺序必须是：硬约束 → 能力 → 兴趣 → 价值观 → 未知。
反过来问会得到一堆无法用于筛选的信息。

**④ 自述与证据分离。**
能力项分「有证据」与「仅自述」两栏。不区分的话，后端匹配就是在拿用户的自我感觉
对企业的硬要求。

**⑤ 未知是一等公民。**
`unknown` 不是失败状态，是合法输出。系统不许猜。
这是与通用聊天机器人最本质的分界线。

### 3. 数据契约

证据分级（五级，全部落库）：

| 值 | 含义 |
|---|---|
| `external` | 外部来源（JD 原文、官方课程目录） |
| `team` | 团队判断，必须带置信度与依据 |
| `user_stated` | 用户自述，且有可验证证据 |
| `unverified` | 用户自述，但无任何证据支撑 |
| `unknown` | 明确未知 —— 合法输出，不是错误 |

五类核心实体：

```
users        匿名用户（demo 阶段不收集姓名/手机号）
responses    每次采集的原始回答。append-only，带 schema_version
profiles     画像快照（解析后的结论），与 responses 分离
jd_records   JD 原文留存。append-only，永不修改
positions    标准化岗位（一条 JD → 一个 position）
requirements 原子化需求（一个岗位多条），带 evidence_span 指回原文
```

**为什么 responses 与 profiles 必须分离**：任何时候用户问「你为什么认为我不能接受出差」，
要能翻出当初填的原文，而不是翻出一句模型总结。

**为什么 responses 要 append-only + schema_version**：问卷字段将来一定改，
没有版本号就无法回溯「这条结论是基于哪版问卷得出的」。

JD 拆解的中间态 `JdExtraction`（不落库，人工确认后才变成 `Position`）：

```
company, title, location, job_type, canonical_name, industry,
variant_names[], work_scenarios[], stressors[],
requirements[{kind: hard|soft, category, text, evidence_span}],
extraction_notes
```

硬约束排除规则（**分级，不可合并**）：

| 不可接受项 | hard 关键词（命中即排除） | soft 关键词（只提示不排除） |
|---|---|---|
| 长期出差 | 出差、驻场、外派、外地办公 | — |
| 高频加班/996 | 加班、996、大小周、单休 | 抗压、节奏快、高强度 |
| 纯销售性质 | 销售、客户开拓、业绩指标、拉新 | — |
| 需要频繁公开演讲 | 路演、主持、对外演讲 | 汇报、演讲 |
| 工作地点不固定 | 多地办公、全国 base | 轮岗、多地 |

> **为什么分级**：「抗压」「节奏快」几乎是所有 JD 的套话。把它们当硬事实会错杀
> 本可行的选项。排除理由是这个系统后果最重的输出，**宁可漏报不可错杀**。

### 7. 匹配算法（确定性）

**不让 LLM 做匹配。** 匹配是这套产品的立论基础：用 LLM 匹配，同一个用户两次提交
可能得到不同结果，且无法解释「为什么说我缺 SQL」。确定性规则可复现、可测试、可逐条解释。

对每个岗位的每条需求（仅 `技能`/`工具`/`软能力` 三类参与比对；`学历`/`专业` 走门槛检查；
`经验`/`证书` 标记为「无法比对」）：

```
cap_id = capabilities_of(requirement.text)     # 可能多项，见第 4 节
若 cap_id 为空        → 无法比对（明确说明原因，不静默跳过）
若用户有该能力且有证据  → 匹配（matched）
若用户有该能力但无证据  → 待验证（unverified）
否则                  → 缺口（gaps），附培养方案可补课程
```

两个公开的覆盖率指标：

```
coverage          = (匹配数 + 待验证数) ÷ 可比对需求数
verified_coverage = 匹配数 ÷ 可比对需求数
```

**这两个都是团队定义的启发式指标，不是标准化测评分数。** 必须在界面上标注，
不伪装成客观。

### 三个统计陷阱及防护（必须实现）

**① 小样本陷阱。** 只有 2 条可比对需求的岗位，2 条全中就得到 100% 覆盖率，
从而打败有 15 条要求、缺 3 条的大样本岗位。这不是「证据更充分」，是题目更少。
**防护**：要求 `n_comparable >= 5` 才能参评，不足的标记「样本不足」而不是给虚高百分比。

**② 岗位族碎片化。** LLM 对同一类岗位给出不同名字（商业分析师 / 战略商业分析师 /
商业分析Leader），直接当独立岗位会让统计虚高、结果列表碎成一地。
**防护**：受控岗位族词表归并（第 6 节），同族只保留证据最强的代表，展示族内样本数。

**③ 通用能力霸榜。** 「沟通」「协作」「英语」出现在大量 JD 里，按被需数量排序会挤掉
具体可补的缺口。
**防护**：硬缺口优先于软能力；培养方案**必修课**排最后（那是既定安排，不构成建议）；
软能力单独分区并明确「选课无法获得」。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 服务状态、LLM 配置、白名单模式 |

| POST | `/api/advice` | 只算建议不落库（前端实时预览用） |
| POST | `/api/jd/parse` | JD → 原子化需求 + 生成后校验。不落库 |
| POST | `/api/jd/confirm` | 人工确认后入库。**要求 `X-Admin-Token`** |
| POST | `/api/jd/fetch` | URL 受控采集 |
| POST | `/api/jd/upload` | 文件导入 |
| GET | `/api/positions` `/api/jds` | 岗位库 / 原文库 |

安全设计（**不可协商**）：

- **写操作 fail-closed**：`ADMIN_TOKEN` 未配置时 `/api/jd/confirm` 直接 401，不放行。
  别为了方便改成默认放行——那是公网部署的删库后门。
- **SSRF 防护**：协议白名单 + DNS 全 IP 校验 + **逐跳重定向校验**
  （否则 302 到 `169.254.169.254` 能绕过首跳检查拿到云主机元数据）。
  IPv4-mapped IPv6（`::ffff:127.0.0.1`）必须先拆开再判断。
- **限流**：`/api/jd/parse` 10 次/分钟（要发外部请求）。
- **LLM 输出永不直接进库**，必须经 `/api/jd/confirm` 人工确认。

### 9. 前端规格

分步向导，一次只面对一件事：

- 步骤条显示进度，已完成步骤打勾
- 第 2 步右栏技能预设随第 1 步的研究方向切换
- 第 4 步价值观合计实时变色（100 绿 / 超出红 / 不足黄）
- 第 5 步未知项给**候选清单**（空白起步会被直接跳过）
- 结果卡结构：结论条 → 方向结论（覆盖率条形图）→ 硬缺口 → 软能力 → 两周行动 → 可折叠 JSON

### 10. 验收标准

按顺序验证，不需要信任何人的话：

1. **跑同一份问卷两次**，方向排序必须一致（确定性引擎保证）
2. **把一项能力从「仅自述」改成「有证据」**，该方向覆盖率必须变化
3. **点开任意一条需求的 evidence_span，回 JD 原文核对是否逐字存在**
4. **把「高频加班」设为不可接受项**，看哪些方向被排除、排除理由是什么
5. **RIASEC 全填同分**，系统必须说「未分化」而不是编一个兴趣码
6. **价值观六个维度全填同分**，系统必须说「无法排序」而不是随便挑一个
7. **问一个资料库外的问题**，系统必须说「未知」而不是编
8. **拔掉 LLM key**，画像与建议必须完整可用，JD 拆解走规则基线并明确标注

第 3 条最硬：它直接检验「系统不输出资料库外的事实」是不是真的。

### 11. 明确不做的事

- **不做岗位聚合、不做投递撮合**。定位是职业认知与决策支持工具。
  以个人身份在中国大陆无法合规公开运营招聘信息站（个人 ICP 备案禁止涉及招聘内容；
  经营性网络招聘服务需《人力资源服务许可证》）。
- **不采集智联 / BOSS 直聘 / 猎聘**。反爬严格（多为 JS 渲染 SPA，本地抓不到正文），
  且批量抓取有合规风险。只采集高校 / 政府 / 企业官网校招页。
- **不做微调、不做多 Agent**。样本量不够，单链已够。
- **不用 MBTI 做方向判定**。只作辅助标签，重测信度约五成、对绩效预测力弱
  （Pittenger 1993），界面必须展示该局限。
- **不让 LLM 直接生成建议**。LLM 只润色措辞，且引用必须通过校验。
