# 任务样例手册：你的交付物长什么样

> 分工表说「交数据契约」「交输出协议」很抽象。这份手册给每个人一个**可以直接照抄的样例**。
> 找到你的那一节，照着样子做就行。

---

## 1. tmj —— 数据契约 + 2 个样板方向

### 你要交的东西 A：数据契约（一页纸）

| 字段 | 类型 | 必填 | 允许值 | 说明 |
|---|---|---|---|---|
| `direction_id` | string | 是 | DIR-001 起 | 方向唯一编号 |
| `name` | string | 是 | — | 方向名称 |
| `cap_id` | string | 是 | DIR-001-CAP-01 | 能力唯一编号 |
| `cap_name` | string | 是 | — | 能力名称 |
| `level` | 枚举 | 是 | 必备 / 加分 / 了解 | 该能力对这个方向的重要性 |
| `evidence_ids` | 列表 | 二选一 | EV-xxx | 要么挂 ≥2 条证据，要么 `status=unknown` |
| `scope_note` | string | 是 | — | 适用范围，如「制造业与零售业」 |
| `ev_id` | string | 是 | EV-001 起 | 证据唯一编号 |
| `ev_type` | 枚举 | 是 | external / team / **user_stated** | external=外部来源；team=团队判断；**user_stated=用户自述（为 v2 个人档案预留，demo 阶段不使用但字段必须存在）** |
| `source_url` | string | external 必填 | — | 来源链接 |
| `captured_date` | 日期 | 是 | YYYY-MM-DD | 采集日期 |
| `excerpt` | string | 是 | — | 原文摘录，≤100 字 |
| `status` | 枚举 | 否 | unknown | 无证据时必须填，不许留空 |

**缺失处理规则（必须写进契约）**：
- 一条能力找不到 ≥2 条证据 → `status` 填 `unknown`，界面显示「待验证」，**不允许填猜测**
- 证据没有可用链接 → `ev_type` 改为 `team`，并在 `excerpt` 里写明判断依据

**为 v2 预留（demo 不实现，但字段现在就定）**：`ev_type` 含 `user_stated`——将来用户自述的信息（「我学完了 SQL」）作为独立证据类型入库，与岗位证据分开存储、分开标注。现在多写一个枚举值，成本为零；等到 v2 再改表结构，等于全套返工。

### 你要交的东西 B：2 个样板方向（填好的表格）

示例（方向：供应链分析）：

| cap_id | 能力 | 级别 | 证据 | 适用范围 |
|---|---|---|---|---|
| DIR-001-CAP-01 | SQL 数据查询 | 必备 | EV-001, EV-007 | 制造业与零售业 |
| DIR-001-CAP-02 | Excel 与数据建模 | 必备 | EV-002, EV-008 | 通用 |
| DIR-001-CAP-03 | 库存/需求预测基础 | 加分 | EV-003, EV-009 | 制造业为主 |
| DIR-001-CAP-04 | 跨部门沟通协调 | 必备 | EV-004, EV-010 | 通用 |
| DIR-001-CAP-05 | ERP/进销存系统认知 | 加分 | EV-005 | 制造业与零售业 |
| DIR-001-CAP-06 | 该方向的真实成长路径 | unknown | — | 待第 6 位审核后补充 |

**注意最后一行**：这就是 `unknown` 的正确用法——我们没把握的，就标出来。**这一行在演示时是加分项，不是丢分项。**

## 2. lsy —— 按契约填 3-4 个方向

你的工作是把 tmj 的两个样板复制成 3-4 份。示例（填一条能力 + 它的两条证据）：

```
cap_id:       DIR-002-CAP-01          # 方向2（数据分析）的第1条能力
cap_name:     SQL 数据查询
level:        必备
evidence_ids:  [EV-011, EV-017]
scope_note:    互联网与零售业数据分析岗
```

```
ev_id:         EV-011
ev_type:       external
source_url:    https://www.zhaopin.com/...（某数据分析岗 JD）
captured_date: 2026-09-23
excerpt:       "熟练掌握 SQL，能独立完成取数、报表与专题分析"

ev_id:         EV-017
ev_type:       external
source_url:    https://...（另一家公司同岗位 JD）
captured_date: 2026-09-23
excerpt:       "日常工作中约 60% 时间为 SQL 取数与数据清洗"
```

**关键要求：两条证据必须来自不同公司或不同来源**，不能同一份 JD 抄两遍——单条 JD 带着公司、地区、时点偏差，两条以上才站得住。找不到第二条时，宁可标 `unknown`，不要凑。

## 3. 第 6 位（在职）—— 审核样板

你要交的是**逐条批注**，每条三行：改了什么 / 为什么 / 依据。示例：

```
CAP-03「库存/需求预测基础」级别：加分 → 改为「必备」
原因：我所在行业（制造业供应链）校招 JD 中，10 份有 8 份要求预测或计划相关课程/项目
依据：本人 2023-2025 年社招与内部转岗观察；公司内部岗位说明书

CAP-05「ERP/进销存系统认知」scope_note：「制造业与零售业」→ 补充「快消与物流业同样常见」
依据：本人在快消供应链部门三年，SAP 与 WMS 为日常工具
```

**不许只写「没问题」**。没有修改也要写「经核对 6 条无误，其中 2 条我补充了行业细节」——否则技术块和汇报都拿不到任何信息。**你的行业判断是我们整个产品里「路径侧」证据的唯一来源。**

## 4. xrr —— 输出协议与质量门槛

你要交三样：**提示词引用约束**、**输出 JSON 协议**、**校验规则清单**。

### 提示词片段（示例）

```
你只能引用以下证据 ID：[EV-001, EV-002, ..., EV-045]。
规则：
1. 每条关键结论必须附 1 个以上列表内的证据 ID；
2. 用户的问题在这些证据中没有依据时，你必须回答「未知」，
   或标注「团队判断：<你的假设>」并说明假设是什么；
3. 禁止生成任何链接；禁止引用列表外的 ID；
   禁止用「一般来说」「通常认为」开头回避问题。
```

### 输出协议（示例）

```json
{
  "recommended": [
    {"direction_id": "DIR-001", "score": 82,
     "score_breakdown": {"技能匹配": 30, "兴趣倾向": 22, "约束符合": 18, "年级匹配": 12},
     "reason": "...", "cited_evidence": ["EV-001", "EV-007"]}
  ],
  "gap_analysis": {"have": [...], "todo": [...], "unknown": [...]},
  "micro_task": {"title": "...", "hypothesis": "...", "cited_evidence": [...]}
}
```

### 校验规则清单（示例 5 条）

| # | 规则 | 违反时 |
|---|---|---|
| 1 | `cited_evidence` 中每个 ID 必须存在于证据库 | 拒绝展示 |
| 2 | 每个 `recommended` 项必须有 `score_breakdown` | 拒绝展示 |
| 3 | 出现不在证据库 `source_url` 中的 http 链接 | 拒绝展示 |
| 4 | `gap_analysis.unknown` 为空但 `todo` 非空 | 警告（可能跳过未知项） |
| 5 | `reason` 中出现「一般来说」「通常认为」 | 标记人工复核 |

## 5. Bruce —— 集成：AI 接入 + 校验层 + 装配

### 校验层（示例，伪代码）

```python
def validate(model_output):
    problems = []
    # 1. 引用的 ID 必须真实存在
    for ev in model_output.all_cited_evidence:
        if ev not in evidence_db:
            problems.append(f"引用了不存在的证据 {ev}")
    # 2. 每条能力要么有证据，要么明确标 unknown
    for cap in output.capabilities:
        if not cap.evidence_ids and cap.status != "unknown":
            problems.append(f"{cap.cap_id} 既无证据也未标未知")
    # 3. 禁止资料库外的链接
    if output.contains_url_not_in_db():
        problems.append("出现资料库外的链接")

    if problems:
        return REJECT, problems      # 拒绝展示 + 记录一次引用违规
    return PASS, output
```

### 装配：把保底 5 步串成一条链

```
输入 8 问 → 映射为评分字段 → rules.score() 取 Top3
        → llm.explain(top3) → 用户选择
        → llm.gap_and_task(选定方向)
        → validate() → 展示
```

**自查标准**：把模型拔掉，用一份预置的 `model_output` JSON 走完 `validate()` 和展示——通了，说明校验层不依赖模型，演示当天 API 挂了也有降级路径。

## 6. lx —— 演示脚本 + 访谈 + 测试

### 保底版演示脚本（10 分钟，含秒数）

```
0:00-1:00   问题背景：学生在"不知道选什么"上的成本（引用 36.2% 数据）
1:00-3:00   小A 回答 8 个问题（预填账号，10 秒过）
3:00-5:00   系统给出 3 个方向 + 分数构成；点开一个方向看证据 ID 与来源链接
5:00-6:30   选供应链分析 → 差距：已有 / 待补 / 待验证
6:30-8:00   两周微任务 + 它要验证的假设
8:00-9:00   ★ 关键 60 秒：故意问一个库外问题
            （"我学机械的能转供应链分析吗？"）→ 系统回答"未知/需补充证据"，不编造
9:00-10:00  对比：同一问题问裸 DeepSeek，展示它如何越界
```

**8:00-9:00 那一分钟是整个演示的灵魂**——它证明的不是我们多聪明，而是我们知道自己的边界。

## 附录：AI 工程体现在哪（汇报用，防止被问倒）

**不要把我们说成「做了一个数据库然后查表」**。三个可见的 AI 工程点：

1. **库外怎么表現，才是主战场**。我们的证据库只覆盖 3-4 个方向，用户一定会问出库外的问题（跨专业、地域、家庭约束、具体公司）。**查不到时不说谎，比查得到难得多**——学术已证这是全行业没解决的事（RCT 显示 AI 生涯智能体反而增加疑虑；79% 用户听从建议但无持续改善）。
2. **约束一个会编的模型，比放任它编更难**。证据 ID + 引用约束 + 生成后校验，这是有工程含量的活；放任模型自由生成才是没有含量的那个。
3. **评估是最硬的证据**。同一问题，我们的系统 vs 裸 DeepSeek/Kimi/Stepfun，逐条标出谁越界、谁引用了不存在的来源——这是 AI engineering 的核心学科，也是全行业空白。

**主动说明的立场**（别被问出来）：我们不微调（数据量不够，也没必要）；不做多 Agent（单链就够）；我们用了检索，但比常规 RAG 更严格（证据 ID  + 生成后校验，而不是检索完就信）。

**诚实的边界**：6 天 demo 尺度上 AI 工程深度有限——demo 证明「价值主张可验证」，模型层的深度（多模型对比的系统化、引用违规率指标、拒答策略优化）是 v2 的主线。这句话主动说，是加分项。

## 附录 B：长期记忆怎么实现，数据怎么变成训练原料（v2 技术预案）

**架构五层（从下往上）**：

```
治理层   查看 / 修改 / 删除 / 关闭 / 导出          ← PIPL 合规，最容易被忘
  ↑
写入层   什么情况写什么
          用户明说 → user_stated（需用户确认后才固化）
          系统推断 → system_inferred（低置信，且不得覆盖 user_stated）
          任务结果 → task_result（只记事实，不生成能力/人格定论）
  ↑
注入层   按任务门控，不是全量塞上下文
          方向推荐 → 稳定事实 + 约束
          差距分析 → 技能状态机
          语气适配 → 偏好设置
          复盘     → 时间线 + 历史记忆
  ↑
检索层   结构化查字段（确定要什么）+ 向量查相似经历（模糊回忆）
  ↑
存储层   profile_store（结构化字段）
         memory_items（半结构化条目 + 向量索引）
```

**记忆条目的数据模型**：

```
memory_item:
  mem_id:        MEM-0001
  type:          user_stated | system_inferred | task_result | feedback
  content:       "SQL 已入门，完成课程 X 与一个小项目"
  evidence_ref:  [EV-012] 或对话轮次编号
  stated_at:     2026-10-15
  valid_until:   2027-06-30      # 年级类信息会过期，到期标"待更新"不默默失效
  confidence:    0.9             # 仅 system_inferred 需要
  confirmed:     true            # 用户是否确认过
  affects:       [skill:sql, direction:DIR-002]
```

**三个关键设计**：
1. **技能是状态机，不是文本**：`sql: 待补 → 学习中 → 已有(2026-10-15, MEM-0001)`。差距分析直接读状态，不去翻聊天记录——否则同一件事在不同对话里说法会不一致。
2. **推断不覆盖自述**：系统推测「可能不喜欢编程」（conf 0.4）与用户自述「我喜欢但不擅长」冲突时，**自述优先，两者都保留并展示给用户**。让用户看见系统对他有什么判断，是信任的前提。
3. **敏感字段最小化**：家庭约束、心理倾向类信息不进推荐逻辑（避免歧视性输出——学术已证语气与推荐会随人口统计特征系统性变化），只用于约束条件的匹配。

**关于「把数据纳入训练」——三个层次，以及一句实话**：

| 层次 | 做什么 | 什么时候做 |
|---|---|---|
| **1. 上下文注入**（不是训练） | 档案按任务门控注入 prompt 或检索上下文。**95% 的收益在这里，零训练成本** | v2 就该做 |
| **2. 监督微调 SFT** | 用 `(档案 + 证据库) → 带证据 ID 的规格式回复` **合成**训练对，固化引用格式、拒答措辞、「不输出库外事实」等行为 | v3 |
| 3. 偏好优化 DPO | 用走查和盲测里的人工对比标记（「A 比 B 好，因为 A 承认了未知」）训偏好 | v3+ |

**三句实话**：
1. **现在和 v2 都不要碰微调。** 几十条样本只会过拟合，且违反数据最小化原则。
2. **不能拿真实用户对话直接训**：① PIPL 要求训练授权与产品使用授权**分开取得**；② 用户对话不等于理想回复；③ 会把我们批判的「无依据建议」原样学进去。
3. **真正现在就该做的事只有一件**：从第一天起，把每次交互按可训练格式落日志——`{输入, 检索到的证据 ID, 模型输出, 校验结果, 用户反馈}`。这个日志既是未来一切训练的**唯一原料**，也是当下最好的评估数据集（引用违规率、拒答率都从它算）。**现在不花 10 分钟定格式，v2 想训时历史数据不可用。**
