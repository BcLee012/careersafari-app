# “职业微体验”：AI赋能的大学生职业探索产品初步方案

适用课程：人工智能+工程管理：AI赋能的系统工程管理  
团队规模：6人  
项目周期：12周  
方案日期：2026年9月21日  
方案阶段：初步需求调研与产品设计

> 本方案以“帮助学生了解职业实际工作”为核心，采用“同一项目、不同岗位”的体验结构。产品名称暂定为“职业微体验”。首版项目情境与岗位组合属于建议设计，需经学生访谈和从业者审核后确定。文中的调研结论来自公开资料检索，尚未完成一手访谈、竞品完整试用或效果实验，因此不会把需求假设写成已经证实的结论。

## 第一部分：产品简介

“职业微体验”面向缺乏相关实习经历、希望了解职业实际工作的大学生，让学生在同一个项目中分别体验两种岗位的典型任务。学生需要阅读工作材料、向AI扮演的客户或同事提问、处理情境变化，并提交简单的工作成果。系统依据经过审核的任务标准提供反馈，帮助学生比较不同岗位的工作内容、协作方式和决策取舍，发现自己原有认识中的偏差，为后续学习、实习和职业探索提供更具体的依据。产品首先追求职业认知的改善，不根据一次体验判定学生是否适合某种职业。

## 第二部分：需求分析、市场定位与主要功能

### 2.1 为什么选择这个问题

大学生接触职业的渠道很多，包括招聘网站、职业介绍、社交平台、学长学姐分享和实习。但“听过一个岗位”与“理解这个岗位如何工作”之间可能存在距离。

例如，学生可能知道产品经理负责需求、项目经理负责进度，却说不清：需求从哪里来、怎样判断优先级、进度受到哪些因素影响、两个岗位在发生冲突时如何协商。招聘信息中的“沟通能力强”“推进项目落地”等表述，也未必能帮助初学者想象实际工作。

本项目拟验证的核心问题是：**缺乏相关实习经历的学生，能否通过短时、可交互的工作任务，更准确地理解目标岗位，并据此决定下一步探索行动？**

这里有三项需要保持区分：

1. **职业认知**：知道工作做什么、为什么这样做、怎样算完成。
2. **当前能力**：目前是否具备完成任务所需的知识和技能。
3. **职业偏好**：了解工作以后，是否愿意继续接触、学习和投入。

学生暂时不会做任务，不代表不适合该职业；学生喜欢一次体验，也不代表已经了解该职业的全部。产品应帮助学生分清这些情况。

### 2.2 初步调研发现与证据边界

本轮检索覆盖教育部及国家大学生就业服务平台、招聘与职业发展产品、牛客、B站、知乎、Forage，以及职业探索相关官方资料。小红书未获得足以支撑具体结论的可核查帖子，不能视为已完成该平台调研。

| 初步发现 | 公开资料依据 | 能说明什么 | 不能直接说明什么 |
|---|---|---|---|
| 大学生就业服务面向较大的潜在人群 | 教育部网站公布2026届普通高校毕业生规模预计1270万人。[1] | 职业与就业服务具有广泛的服务对象 | 毕业生人数不等于产品用户数，更不等于付费市场规模 |
| 测评、岗位匹配和简历指导已有公共供给 | 国家大学生就业服务平台公布了相关服务。[2] | 单纯增加通用测评和岗位推荐，难以形成明显区别 | 不能据此判断所有学生都使用过这些服务，或这些需求已被完全满足 |
| AI求职工具已覆盖岗位分析等功能 | 智联求职AI官方页面展示筛选岗位、分析岗位要求和优化简历等功能。[3] | 求职阶段已有较直接的AI产品供给 | 官方功能宣传不能证明实际准确率或求职效果 |
| 职业模拟已有产品先例 | Forage提供企业参与设计的模拟任务，学生提交成果后可对照参考答案。[4] | “通过任务认识工作”是已有产品形式 | 不能把职业模拟本身宣称为本项目独创，也不能直接照搬其效果宣传 |
| 工作日常有内容吸引力，也存在认知变化的个案 | B站有岗位体验视频；牛客有从运营转到产品后逐步认识工作的个人叙述。[7][8] | 可用来发现问题、设计访谈提纲 | 播放量不等于付费意愿，个人经历不代表大学生整体 |
| 工作预览应呈现工作中的多面性 | 美国人事管理局介绍的真实工作预览强调呈现工作的积极与消极方面，帮助个人判断。[9] | 可以借鉴其内容设计原则 | 招聘场景的结论不能直接证明本产品对中国大学生有效 |

因此，“大部分学生不了解职业细节”目前仍是待验证判断。本方案更谨慎的表述是：**已有资料提供了职业认知不足的线索，值得针对具体人群进一步调查。**

### 2.3 把需求拆成可以设计和验证的问题

| 需求维度 | 学生可能遇到的疑问 | 产品应帮助形成的认识 |
|---|---|---|
| 典型任务 | “这个岗位一天到底要处理什么？” | 常见任务、工作流程及其目的 |
| 工作材料 | “开始工作时，我会拿到什么？” | 需求单、邮件、数据表、会议纪要等材料的用途 |
| 工作产出 | “做完以后要交什么？” | 交付物的形式、使用者和质量要求 |
| 协作关系 | “为什么总要开会、追问或协调？” | 不同岗位掌握的信息和承担的责任 |
| 决策取舍 | “时间不够、需求又变了，怎么处理？” | 时间、质量、成本与范围之间的关系 |
| 工作感受 | “哪些活动让我投入，哪些让我疲惫？” | 对具体工作活动的体验，而非对岗位名称的好恶 |
| 岗位差异 | “产品助理和项目助理究竟差在哪里？” | 同一项目中不同岗位的关注点和工作边界 |
| 后续探索 | “体验之后，我还需要了解什么？” | 尚未覆盖的问题和可执行的下一步行动 |

需求调查还应寻找反例。例如，有的学生已经很了解岗位，却因时间、经济条件或招聘机会受限而无法行动。这些问题不能靠职业体验解决，不应为了证明产品有用而归入同一种需求。

### 2.4 目标人群与使用场景

#### 2.4.1 核心用户

首版优先服务同时满足以下条件的大学生：

- 缺乏目标岗位的相关实习或工作经历；
- 对两个相关岗位已有初步兴趣，但难以说清工作差异；
- 愿意投入一段短时间进行探索；
- 希望在选择课程、项目或实习方向前增加了解。

用户可以来自不同专业，不以年级作为唯一划分标准。例如，大二学生和准备跨专业求职的大四学生，都可能处于相似的职业认知阶段。

首版对完全没有探索方向的学生，只提供简短的项目说明和岗位入口。是否增加更全面的探索引导，应由调研结果决定。

#### 2.4.2 优先场景

| 使用场景 | 用户触发点 | 产品希望提供的帮助 |
|---|---|---|
| 选择实习方向前 | 想投递实习，但分不清两个岗位 | 理解工作差异，确定下一步重点了解的方向 |
| 生涯课程实践 | 老师希望学生从听介绍转向参与任务 | 提供可完成、可讨论、可复盘的体验材料 |
| 阅读招聘信息后 | 能看懂职责文字，却无法想象实际工作 | 把抽象职责放回具体情境 |

需要区分直接用户与组织方：学生使用产品，教师、就业指导中心或学生组织可能负责组织体验。组织方是否愿意采用，取决于内容可信度、教学便利性和效果证据，需要单独访谈。

### 2.5 现有产品和替代方式已经解决了什么

产品不能只与其他AI应用比较，还应与学生现在使用的全部办法比较。

| 产品或方式 | 已有实现或作用 | 对本项目的启示 | 需要进一步核查的问题 |
|---|---|---|---|
| 国家大学生就业服务平台 | 生涯测评、岗位匹配、简历优化等公共服务。[2] | 通用推荐已有供给，首版集中处理具体工作认知 | 学生是否知道并使用，使用后还缺少哪些信息 |
| 智联求职AI | 岗位筛选、岗位要求分析、简历优化等。[3] | 把主要探索放在学生尚未理解工作内容的阶段 | 岗位分析能否已经满足目标学生的认知需求 |
| 国内职业发展平台，如职场派 | 官方展示职业规划、学习计划和模拟面试等功能。[10] | “加入AI对话”不足以构成差异化 | 其实际体验是否已有类似的工作情境模块 |
| Forage | 企业参与设计的职业模拟、任务提交与参考答案；也有项目管理相关模拟。[4][5] | 不能把任务模拟本身作为创新点，需要探索新的组合和适用场景 | 同项目双岗位比较和认知复盘是否比现有形式更有价值 |
| 职业视频和经验帖 | 展示他人的工作片段与感受。[7][8] | 增加用户亲自提问、选择和处理材料的机会 | 用户是否愿意为主动体验付出比观看更高的时间成本 |
| 通用AI聊天工具 | 可通过提问获得职业说明或角色扮演 | 需要用经过审核的内容、稳定的任务流程和可检查的反馈体现价值 | 学生直接使用聊天工具是否已经足够 |
| 实习、校友访谈、企业参访 | 提供接触真实人员和工作环境的机会 | 线上体验可以作为准备或补充 | 学生获取这些机会的困难、成本和已有收获是什么 |

这张表是初步比较，不是完整竞品测评。公开页面未展示某功能，并不意味着该产品一定没有该功能。后续应选取少量代表性产品完成实际体验，再更新判断。

### 2.6 市场定位与潜在采用路径

暂定定位：**面向实习前职业探索的短时工作体验工具，通过同一项目中的不同岗位，帮助学生理解任务、协作与取舍。**

首版的直接目标是让一小批学生获得可验证的职业认知改善。潜在采用路径包括：

1. 在一门生涯课程或一个学生组织中组织体验，获取集中反馈；
2. 在验证内容和流程后，开放给学生自主使用；
3. 若存在明确需求，再探索教师课程包或学校服务；
4. 更长期可探索企业参与提供案例，但应保留对工作困难和局限的真实呈现。

Forage公开说明其学生服务免费，企业合作方付费承载项目，说明企业付费是一种已有商业路径。[6] 对本项目而言，学校采购、学生付费和企业合作都还没有得到验证。课程阶段不以预测收入证明项目成立，而应先明确谁会使用、为何使用、使用后得到什么。

### 2.7 拟探索的差异化优势

#### 2.7.1 同一项目、不同岗位：让学生理解分工

独立的岗位介绍可能使用不同背景和例子，学生难以直接比较。首版让两个岗位共同面对一个项目，复用部分材料，同时呈现不同职责、信息和产出。

例如，产品助理关注用户问题和需求优先级，项目助理关注任务依赖、资源和进度。学生可以看到同一项需求变化为什么引起两种不同的工作。

预期价值是降低比较的理解成本。需要验证学生能否在体验后更准确地解释岗位区别，而不只是记住两个职位的定义。

#### 2.7.2 可追问的协作：让学生经历信息获取

职业视频通常由观众接收内容。本产品希望让学生根据问题主动追问：用户为什么提出这个需求、开发方缺少哪些资源、哪些约束不能改变。

AI的作用是依据预设事实作出回应。它不能随意创造项目事实，也不应一开始就把所有答案交给学生。

预期价值是帮助学生理解沟通如何影响工作。需要验证这类互动是否带来额外认识，还是仅仅增加了对话步骤。

#### 2.7.3 真实工作取舍：呈现有成就感和令人费力的部分

体验既包含解决问题，也包含核对信息、修改文档、等待反馈和协调冲突。情境中的事件应来自从业者核实的典型问题，不能为了戏剧效果不断制造危机。

预期价值是帮助学生形成较完整的工作预期。需要验证任务是否具有代表性，以及简化后是否造成新的误解。

#### 2.7.4 认知复盘：把任务完成转化为职业认识

系统保存学生体验前的理解，再结合其任务过程和体验后反馈进行对比。输出重点包括：原先以为是什么、实际体验到了什么、哪些部分还没有覆盖。

预期价值是让学生带走清楚的认识和问题。体验后决定继续了解某岗位，或有依据地暂时放下该方向，都可能是有效结果。

**上述四点是拟形成的优势，尚未证实优于现有产品。** 本项目的差异化主要在服务对象、内容组织和使用流程的组合，需要用实际比较来判断价值。

### 2.8 主要功能及其需求依据

| 功能 | 回应的需求 | 首版实现 | 用户产出 |
|---|---|---|---|
| 体验前认知记录 | 不清楚自己知道多少 | 少量开放问题与熟悉度自评 | 初始认识和探索问题 |
| 项目与岗位介绍 | 不理解任务背景 | 项目目标、角色、约束与材料说明 | 对情境和责任的基本理解 |
| 工作任务体验 | 缺少实际参与机会 | 每岗位2—3个相互关联的步骤 | 一页结构化工作成果 |
| AI角色对话 | 不理解协作与追问 | 每次明确对话对象及其已知信息 | 问答记录和澄清结果 |
| 分层提示 | 缺少基础导致无法继续 | 术语说明、方法提示、填写模板 | 辅助使用记录 |
| 情境变化 | 不理解工作中的约束变化 | 一个经过设计和审核的变化事件 | 调整后的方案及理由 |
| 有依据的反馈 | 不知道遗漏和取舍在哪里 | 根据评价标准引用具体内容点评 | 可检查的反馈与修改建议 |
| 双岗位比较与复盘 | 难以比较岗位和自身感受 | 并列展示任务、行为、感受与未知项 | 职业认识变化和下一步行动 |

首版不必包含复杂账号体系、社交功能或教师管理后台。若试用需要保存结果，可先使用匿名参与编号，减少无关开发工作。

### 2.9 一个完整的体验示例

以下是原创教学情境，需从业者审核后使用。它只展示两类岗位的部分工作，不能代表所有企业中的产品或项目岗位。

**共同背景：**某校园预约系统计划两周后上线。使用方提出新增需求，开发资源有限，试运行中又出现用户投诉。

| 阶段 | 产品助理视角 | 项目助理视角 |
|---|---|---|
| 接收材料 | 用户反馈、初版需求、简化使用数据 | 排期、人员安排、任务依赖 |
| 初步处理 | 区分用户遇到的问题和用户提出的解决办法 | 识别关键依赖、责任不清和进度风险 |
| 追问协作方 | 向AI使用方确认场景、影响范围和真正目标 | 向AI开发负责人确认资源、工期和可调整项 |
| 遇到变化 | 新需求与原定目标或资源发生冲突 | 核心人员临时无法按原计划参与 |
| 提交成果 | 需求优先级、需要继续核实的信息及理由 | 调整计划、风险清单和沟通安排 |
| 复盘 | 如何理解用户问题、如何判断需求价值 | 如何追踪依赖、协调资源和说明风险 |

建议每个岗位先设计为20—30分钟，两个岗位加比较复盘约50—70分钟。实际时间需经测试调整，也允许学生分两次完成。

学生进入第二个岗位时会更熟悉项目，因此完成速度不能直接解释为更擅长该岗位。用户测试可交替安排体验顺序，并在分析中记录这种影响。

### 2.10 首版范围与明确边界

12周内的目标是完成：一个项目、两个岗位视角、一套人工审核的情境材料、一个可运行网页原型，以及一轮用户测试。

优先保证从进入情境到完成复盘的完整过程。职业数量、语音交互、更多事件和教师端统计都属于后续扩展，只有在核心体验通过验证且时间允许时再做。

体验结果不用于招聘筛选，不生成职业成功概率或人格定论。反馈应写成“你在这次任务中没有确认人员可用时间”，而不是“你缺乏项目管理能力”。

对于难以在线呈现的工作，如长期人际关系、现场操作、身体负荷和组织文化，应在复盘中明确说明没有覆盖，并建议通过访谈、参访或实习继续了解。

### 2.11 如何验证需求与产品价值

#### 2.11.1 开发前的访谈

建议访谈约12名学生，覆盖无相关实习经历者，以及刚完成第一次相关实习者；另访谈约4—6名从业者，尽量覆盖两个候选岗位和不同组织环境。这是探索性样本，不用于推算大学生总体比例。

学生访谈围绕最近一次真实选择展开：

- 最近想了解哪个岗位？为什么？
- 能否描述该岗位的一项任务、输入材料和最终产出？
- 用过哪些资料或工具？解决了什么，仍不清楚什么？
- 这种不清楚是否影响了实际决定？有没有采取其他办法？
- 有实习经历后，哪些认识发生了变化？

从业者访谈重点回顾最近一次具体工作：任务如何开始、需要哪些信息、与谁协作、怎样判断完成，以及新人最容易误解什么。使用公开、脱敏或重构的材料，不索取企业机密。

开发前先做人工体验测试：由团队成员在后台扮演角色，让少量学生完成任务。如果内容本身没有带来新认识，先修改内容，再接入AI。

#### 2.11.2 原型阶段的测试

可先招募约24—40名目标学生作为探索性试用，随机分为阅读职业材料和互动体验两组。尽量保持内容范围与时间投入相近，并记录实际用时和完成情况。这个规模是课程执行建议，不是统计功效计算结果；不能据此保证得出显著差异或普遍结论。

| 评价问题 | 观察方法 | 解读边界 |
|---|---|---|
| 是否更了解工作 | 体验前后用难度相近的问题，请学生描述任务、交付物和协作关系 | 不仅依赖“感觉更了解”的自评 |
| 是否修正误解 | 比较前后认识，由人工按预先制定的标准判断 | 不能把所有观点变化都算作改善 |
| 是否区分两个岗位 | 让学生解释同一变化对两个岗位的不同影响 | 避免只考记忆产品中的固定措辞 |
| 是否愿意使用 | 记录开始、完成、退出位置与原因 | 完成率受招募方式和课程要求影响 |
| 反馈是否可靠 | 从业者或经校准的评阅者检查反馈 | 用户喜欢反馈不等于反馈准确 |
| 是否产生后续行动 | 经同意在一周后询问是否查看材料、访谈或继续体验 | 短期行动不等于就业效果 |

评阅者尽量在不知道分组的情况下评价学习结果，部分样本由两人分别评分，讨论不一致原因。产品内AI不作为证明产品效果的唯一裁判。

阅读与互动体验的比较检验的是整个方案的增益，不能单独归因于AI。若时间允许，可另外比较固定分支情境与AI互动情境，判断AI是否具有必要的额外价值。

### 2.12 什么情况意味着需要调整方向

- 如果学生已经能准确理解岗位，主要困难是获取实习机会，应重新评估目标人群。
- 如果阅读简洁材料就能获得相近效果，应简化产品，降低开发和使用成本。
- 如果双岗位体验过长，可允许分次完成，但仍保留比较与复盘。
- 如果学生只记住案例、不能理解工作规律，应修改引导和评价问题。
- 如果从业者认为情境失真，应减少戏剧化事件，重新设计材料。

需求验证的目的也包括发现方案不成立的部分，不能只收集支持性反馈。

## 第三部分：AI技术方案——数据准备、训练与使用流程

### 3.1 技术路线与基本原则

建议首版使用现有大模型，通过API接入网页应用。API可以理解为应用向模型发送请求并取得回答的接口。模型供应商根据中文对话质量、结构化输出稳定性、费用和实际数据处理要求进行小规模比较后选择。

基本运行过程如下：

```text
经过人工审核的情境、角色和评价标准
                  ↓
网页接收学生操作 → 后端读取任务状态与相关资料
                  ↓
大模型生成角色回应、提示或反馈
                  ↓
程序检查格式与关键事实 → 向学生展示结果
                  ↓
保存必要的任务记录 → 支持比较与复盘
```

后端负责保管进度、时间、资源和任务提交状态。大模型负责语言交互和辅助解释。不要让模型自由决定项目预算、改变工期或自行宣布学生通过所有任务。

首版不需要多个自主运行的智能体。不同角色可以共享同一模型，通过不同角色说明和受限信息实现，便于控制成本和排查错误。

### 3.2 数据从哪里来，怎样形成情境包

每个情境包包含六类内容：

| 内容 | 具体字段或材料 | 主要来源与审核方式 |
|---|---|---|
| 岗位说明 | 工作目的、职责边界、典型协作对象 | 公开岗位资料与从业者访谈相互核对 |
| 项目事实 | 目标、期限、人员、约束和已有进展 | 原创或脱敏重构，由从业者审核合理性 |
| 工作材料 | 表格、邮件、需求单、会议记录 | 原创教学材料，检查是否足够完成任务 |
| 角色信息 | 角色目标、已知信息、可透露信息、不知道的内容 | 根据情境设计，避免角色无所不知 |
| 事件与状态 | 发生条件、变化内容、对任务的影响 | 人工明确规则，交由程序控制 |
| 评价标准 | 必查项、可接受的不同方案、常见遗漏、反馈示例 | 由团队与从业者共同制定 |

每份材料记录来源、适用岗位、适用企业情境、审核人和版本日期。公开资料不能自动视为可随意复制，优先编写自己的教学材料，保留必要引用，不直接搬用竞品完整任务或答案。

首版资料较少，可以直接加载当前任务需要的内容。资料增多后再引入检索增强生成，即先从知识库找到相关材料，再提供给模型回答。建立知识库或修改提示词都不等于训练模型参数。

### 3.3 模型输入与输出

| 环节 | 输入 | 输出 | 检查重点 |
|---|---|---|---|
| 角色对话 | 角色说明、允许知道的事实、当前状态、学生问题及必要历史 | 角色回应、引用的事实编号、是否需要澄清 | 是否泄露其他角色信息、捏造事实或越权改变状态 |
| 分层提示 | 当前任务、学生卡点、已使用提示 | 术语解释、方向提示或模板 | 是否直接代替学生完成关键选择 |
| 作品反馈 | 学生提交、评价标准、项目事实、辅助使用记录 | 做到的部分、具体遗漏、修改建议及证据 | 是否基于作品，是否允许多种合理方案 |
| 职业复盘 | 初始认识、体验记录、学生自述感受 | 认识变化、岗位差异、未知项和下一步探索 | 是否把单次表现扩大为长期能力或人格判断 |

基础信息只收集为体验服务的内容，如是否有相关经验、术语熟悉程度。不把姓名、学校排名、性别等作为推断职业适合度的依据。

### 3.4 首版怎样优化模型使用效果

首版推荐采用以下流程，而不从零训练大模型：

1. **建立人工基准。** 先写出典型问题、正确事实和可接受回答范围，明确哪些问题只能回答“情境未提供”。
2. **编写角色与反馈说明。** 规定角色边界、语言风格、允许使用的材料和反馈格式。
3. **准备开发案例。** 包含正常提问、模糊提问、反复追问、要求泄露答案、与任务无关的输入等。
4. **运行并分析错误。** 按事实错误、角色越界、无依据评分、提示过度和无法继续任务等类别记录。
5. **修改内容或程序。** 知识缺失先补材料，状态混乱先改程序，只有表达或指令执行问题才主要调整提示词。
6. **使用保留案例检验。** 一部分测试案例不用于反复修改，最终检查系统是否只对熟悉问题有效。

这一过程属于应用层优化与评测，不应在汇报中称为大模型训练。

### 3.5 如果课程要求训练模型，可增加什么

目前尚未确认课程是否要求参数训练，因此以下为可选分支，不列为首版必须完成的工作。

一个边界较清晰的选择是训练“任务行为分类器”：根据学生提交的短文本，识别其中是否包含需求澄清、风险识别、证据引用或行动安排。它只帮助定位反馈依据，不用于判断学生适合什么职业。

训练过程可安排为：

1. 定义少量行为类别，写清正例、反例和模糊情况；
2. 从原创案例、经同意使用的脱敏样本中整理训练材料；AI生成样本必须标明来源并由人工检查；
3. 两名成员独立标注一部分数据，先解决标准分歧；
4. 按参与者或案例来源划分训练集、验证集和测试集，例如60%、20%、20%，避免同一作品的相似改写落入不同集合；
5. 比较关键词规则、现有模型直接判断和一个轻量分类模型；根据数据量选择简单模型，必要时再考虑小模型微调；
6. 用独立测试集报告各类别的准确识别情况、遗漏和误判，检查跨案例表现；
7. 只有当效果或成本确实改善时才接入产品，否则保留更简单的方法。

所需样本数取决于类别数量和难度。只有几十条样本时，优先用于梳理标准与测试，不应声称训练出了具有普遍能力的职业评价模型。真实学生记录不默认用于训练，参与产品试用与同意训练用途需要分开说明。

### 3.6 学生怎样使用产品

1. 阅读项目和岗位简介，了解体验时长与覆盖范围；
2. 回答少量初始问题，记录自己对工作的认识；
3. 进入第一个岗位，阅读材料，向指定AI角色提问；
4. 根据需要使用解释、提示或模板；
5. 提交方案，在情境变化后作出调整并解释理由；
6. 查看依据明确的反馈，记录自己的感受；
7. 体验第二个岗位，查看两者差异；
8. 完成复盘，选择一个后续探索行动。

可以允许学生使用AI辅助，但要让学生保留关键选择和理由，并记录辅助情况。学生借助大量提示完成的结果，不能与无提示结果直接比较为能力高低。产品无需依靠监控外部工具使用来运作，也不应把无法观测的行为当作已知事实。

### 3.7 AI在研发和使用中的作用

| 阶段 | AI可协助的工作 | 人类负责的判断 |
|---|---|---|
| 调研 | 整理访谈文字、归纳主题、列出不同观点 | 核对原文、判断需求是否成立、保留反例 |
| 内容设计 | 起草情境、任务材料和反馈示例 | 审核真实性、代表性、任务难度和使用权限 |
| 开发 | 辅助界面、代码、测试案例编写 | 检查实现、处理关键状态、验收完整流程 |
| 使用 | 角色回应、适量提示、依据标准反馈 | 学生作出选择；团队负责标准与质量复核 |
| 评价 | 辅助汇总结果和发现错误类别 | 独立评价效果，不能让产品自证有效 |

### 3.8 可靠性、成本与数据处理

- **事实可靠性：**关键事实由程序或情境材料提供；资料没有的信息明确说明未知。
- **输入边界：**学生提交和材料中的文字视为内容，不允许其覆盖系统角色和任务规则。
- **反馈可靠性：**要求指出作品中的具体依据；对开放任务给出多种可接受思路，避免把参考答案当成唯一答案。
- **运行保障：**设置单次输出长度、对话轮次和重试上限；模型不可用时提供静态说明，保存已完成进度，明确标注降级状态。
- **数据最小化：**采用匿名编号，提前说明保存内容、用途和期限；限制记录访问权限，提供退出和删除联系渠道。
- **外部模型：**只传送完成任务所需的信息，不输入真实企业机密；使用前核对供应商的数据处理设置。
- **成本测量：**先记录若干完整体验的输入、输出用量，再按实际模型价格估算。总成本约为完整体验次数乘以单次平均调用成本，再加部署费用和必要余量。模型价格与预算待选型后填写，不在本方案中虚构固定费用。

## 第四部分：团队分工与12周工作日程

### 4.1 六人分工

以下用成员编号占位，确定人员后替换姓名。每人有主要职责，同时参与必要的交叉审核。

| 成员 | 主要职责 | 核心交付物 | 重点协作 |
|---|---|---|---|
| 成员1：需求与产品 | 学生访谈、需求分析、功能优先级、用户流程 | 访谈摘要、需求清单、流程原型 | 与成员2核查需求，与成员6确定评价指标 |
| 成员2：岗位内容 | 从业者访谈、情境包、任务材料、评价标准 | 两岗位内容包、来源与审核记录 | 与成员5检查角色边界，与成员1调整难度 |
| 成员3：前端开发 | 页面、材料阅读、对话和提交界面、结果展示 | 可运行网页与完整用户流程 | 与成员4对接数据，与成员6处理可用性问题 |
| 成员4：后端开发 | 任务状态、数据存储、接口、部署和调用控制 | 稳定任务流程、存储与运行环境 | 与成员5接入模型，与成员3对接界面 |
| 成员5：AI与评测 | 模型选型、角色说明、反馈机制、错误测试 | AI模块、测试案例、错误改进记录 | 与成员2校准反馈，与成员4保证事实一致性 |
| 成员6：测试与项目协调 | 排期、风险跟踪、试用组织、结果分析和汇报整合 | 进度记录、测试报告、最终演示材料 | 全员参与，不由一人独自承担全部测试 |

每项核心功能至少有一名非作者检查。岗位真实性优先邀请从业者审核，不能仅由AI或开发人员自评。

### 4.2 十二周日程

| 周次 | 主要工作 | 主要负责人 | 交付物与检查点 |
|---|---|---|---|
| 第1周 | 明确假设、准备访谈、检查竞品、建立任务看板 | 1、2、6 | 访谈提纲、竞品记录、初版范围；确认课程是否要求训练 |
| 第2周 | 学生与从业者访谈、分析反例、确定首版岗位 | 1、2，全员协助 | 需求依据、岗位选择理由；若核心需求不成立，及时调整 |
| 第3周 | 编写共同项目、两岗位任务与评价标准 | 2、1、5 | 情境包初稿、用户流程；每项任务有输入和产出 |
| 第4周 | 人工扮演角色进行少量体验测试，修改内容 | 1、2、6 | 修订情境、范围冻结；学生能理解并完成主要步骤 |
| 第5周 | 搭建网页、后端状态与一个岗位的最小流程 | 3、4、5 | 从进入任务到提交成果的可运行版本 |
| 第6周 | 完成AI角色对话、提示和作品反馈 | 5、4、2 | 一个岗位完整可体验；检查事实、角色与评分依据 |
| 第7周 | 接入第二岗位、比较复盘、必要记录 | 3、4、5、2 | 双岗位完整原型；停止增加非必要功能 |
| 第8周 | 从业者审核、事实与异常输入测试、费用测量 | 2、5、6 | 问题清单、修改记录、单次体验成本估计 |
| 第9周 | 少量学生预试用、调整时长与测试流程 | 1、6，全员修复 | 稳定测试版本、预先确定的评价标准 |
| 第10周 | 组织分组试用，记录用时、学习结果和退出原因 | 6、1，全员协助 | 匿名试用数据、反馈记录；不随意改变组间条件 |
| 第11周 | 后续行动访谈、人工评阅、分析结果、必要修复 | 6、1、2、5 | 效果分析、证据局限与改进建议 |
| 第12周 | 固定演示版本、准备课程汇报、归档与交接 | 全员 | 可演示产品、方案、评测总结、项目管理记录 |

以上默认每人能持续投入课外时间，具体每周可投入工时尚未确认。第一周应按实际工时重新估算工作量。关键顺序是先验证需求和内容，再扩大技术实现；界面草稿和基础框架可提前准备，但不能替代内容验证。

### 4.3 阶段验收与缩减规则

| 节点 | 继续推进需要满足的条件 | 未满足时的处理 |
|---|---|---|
| 第2周结束 | 能说明目标用户、具体认知缺口和现有方式为何不足 | 缩小用户范围或调整问题，不急于全面开发 |
| 第4周结束 | 内容通过基本真实性审核，学生能完成并说出新的认识 | 修改任务和材料，减少复杂事件 |
| 第7周结束 | 两岗位能完整运行，状态和成果可保存 | 暂停扩展，集中补齐流程 |
| 第9周结束 | 严重事实错误和阻断流程的问题已处理，测试标准明确 | 延后正式测试，缩小功能或使用受控备用流程 |
| 第11周结束 | 结果可追溯，能区分认知改善、满意度和局限 | 如实报告证据不足，不夸大效果 |

若进度紧张，按“视觉装饰、语音、多事件、复杂后台、可选训练模块”的顺序考虑缩减。优先保留共同情境、两个岗位的核心任务、比较复盘和内容审核。

### 4.4 主要风险与应对

| 风险 | 早期信号 | 应对方式 |
|---|---|---|
| 找不到可靠从业者 | 情境只有网上文章和AI生成内容支持 | 选择更容易接触从业者的岗位；无法核实的内容标明局限 |
| 任务过难或过长 | 大量学生卡在术语、格式或工具操作 | 降低工具门槛、提供模板、减少任务数量 |
| AI回应不稳定 | 事实矛盾、泄露答案、忽略约束 | 缩小角色可见信息、用程序管理事实、保留固定回应 |
| 体验好玩但没有认知改善 | 满意度高，岗位理解测试没有变化 | 增强任务与工作职责的联系，调整复盘和内容 |
| 把初学者表现当适合度 | 反馈出现“你不适合”等概括性判断 | 限制结论范围，检查反馈证据，人工抽查 |
| 开发范围膨胀 | 不断新增岗位、语音、社交或推荐 | 第4周冻结范围，新增需求先记录为后续版本 |
| 测试招募不足 | 第8周仍没有明确参与渠道 | 提前联系课程或学生组织；样本不足时按可用性测试报告 |
| 调用费用或网络影响试用 | 单次对话过长、频繁失败 | 限制上下文和轮次、保存进度、提供明确的降级方案 |

### 4.5 如何体现系统工程管理

项目应保留一条从需求到验证的对应关系。例如：

> 学生分不清岗位分工 → 设计同项目双岗位体验 → 明确两岗位材料和任务 → 开发比较复盘 → 用岗位差异题和访谈检查理解是否改善。

团队每周进行一次简短评审，记录已完成工作、阻碍、下一周交付和需要修改的范围。重要调整写清原因和影响，如增加事件会增加哪些内容审核、开发和测试工作。

课程汇报不仅展示界面，也展示需求证据、方案取舍、AI与程序的分工、测试结果和局限。这些内容能够体现团队如何在时间、资源、真实性和效果之间进行管理。

### 4.6 最终交付物

1. 一个可完整体验两个岗位的网页原型；
2. 一个经审核的共同项目情境与两岗位任务包；
3. 需求访谈、竞品比较和功能选择依据；
4. AI使用方案、关键测试案例及问题修复记录；
5. 用户试用和效果分析，明确样本与结论局限；
6. 六人分工、排期、风险与变更记录；
7. 课程演示与后续改进建议。
