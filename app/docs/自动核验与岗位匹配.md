# 自动核验与岗位匹配（0.3）

本说明是当前实现规则。README 与旧原理说明中的「逐条人工确认、最高分代表 JD、能力覆盖率」属于 0.1 历史方案，已被本说明替代。

## 使用流程

1. 启动现有 Web 应用。岗位库页面填写管理令牌、完整 JD 和来源 URL，点击「自动检查并保存」。
2. 程序核对来源原文、字段类型与引用；AI 审查结论是否由引用支持，并按任务和产出确定主岗位族。
3. 全部通过：保存派生岗位。存在疑点：最多一次自动修正，再检查；仍失败进入待确认队列。
4. 学生选择实习或校招，填写已经取得的学历。能力可以暂不填写；系统不会自动赋 3 星。
5. 实践经历可填写自己负责的部分、产出和作品链接/材料编号；材料引用不等于已核实掌握。
6. 报告按多个企业的岗位画像给出至多三个探索方向、证据、未知项和补信息动作。

需重启服务以载入代码和新增表。数据库更新只增加表与列，保留既有 JD、画像和原始回答。旧派生岗位可以浏览，但正式匹配要求重新经过新流程。

## 自动化与失败处理

- 来源一致性：提交原文与来源网页正文对应，或与服务端企业采集器保存的原文快照对应。客户端不能声明「来源已通过」。
- 原文检查：每个需求附引用；零需求、错误类别、错误 kind、找不到引用，不能自动入库。不把失败项改成团队判断。
- 语义检查：逐项返回 supported/unsupported/unknown；缺项、重复项、模糊回答均不能通过。引用出现过，不代表支持更具体的能力要求。
- 工作任务、压力来源只保留原文；生成的日常案例不作为真实岗位事实。
- 社招排除；招聘阶段不明进入待确认。实习与校招建独立画像。
- 企业、发布日期、招聘阶段有正文或官方来源字段依据；主岗位族必须有职责依据。发布日期不明可以保存检查通过的岗位，但不计入近24个月门槛。
- 相同原文、来源、模型配置和规则版本复用检查结果。失败状态不会每次浏览自动重试；点击重查才重新处理。
- 原文不会改写；检查输出、原因、规则版本与模型记录在检查表和追加交互日志中。
- 暂不使用 AI 润色普通报告，减少重复调用。

来源核对只证明文本一致，不保证职位仍在招或真实工作与 JD 相符。AI 审查本身也需要少量真实样本质量抽查。

## 岗位画像门槛

按「主岗位族 × 招聘阶段」汇总：

- 近24个自然月，至少6份有效去重 JD，来自至少3家企业。
- 内容、同一来源 URL、同企业相同任务/要求正文去重；保留 URL 中真正的岗位编号，剔除跟踪参数。
- 同一能力至少被2家企业原文支持，才进入跨企业共现候选能力矩阵。
- 单企业要求单独展示，不传播成整个岗位族的统一要求。
- 日期未知、过期窗口、未检查的旧岗位、社招不计入门槛。
- 门槛是运营规则，不能宣称行业代表性；共现不等于行业必备能力。

当前能力归一仍使用本地受控词表。可以判断已有证据与能力领域的交集，不能判断熟练度完全达到 JD 要求。O*NET 31.0 已接入职业知识检索，与国内 JD 的准入和排序分开。详见 [本阶段方法说明](../../docs/岗位覆盖与匹配方法.md)。

## 用户信息状态

| 状态 | 含义 |
|---|---|
| artifact_provided | 有实践描述和作品引用；贡献、真实性、熟练程度待核实 |
| course_or_self_report | 课程学习或自述，来源独立记录 |
| unknown | 未填/明确不确定，不能算缺口 |
| confirmed_gap | 用户明确说明尚不会，才进入补能力建议 |

旧 verified 字段仅保留兼容；勾选「有经历」不会把能力设成已验证。API 报告保留 coverage/verified_coverage=null，前端不显示匹配百分比。

学历在读不自动当作已取得硕士；“相关专业”不自动证明专业符合。岗位资格与方向探索分开；资格未知附提示。

## 接口与开发验证

- POST `/api/jd/ingest`：自动检查保存，返回 ready/review/excluded；需要管理令牌并限流。
- POST `/api/jd/confirm`：兼容旧接口，仍经过同一套检查，不信任客户端 confidence。
- GET `/api/jd/reviews`：待确认队列，需要管理令牌。
- POST `/api/jd/{jd_id}/retry`：重新处理保存的原文，需要管理令牌。
- POST `/api/jd/parse`：结构/引用预览，规则基线只能用于演示，不是自动入库完成标记。
- POST `/api/profile`、`/api/advice`：`answers.target_stage` 为实习或校招，默认实习；`attained_degree` 是已取得学历。

回归检查（临时数据库与固定响应，不使用真实模型额度）：

```sh
app/.venv/bin/python -m unittest discover -s app/tests -v
node --check app/static/app.js
```

浏览器检查使用现成 Playwright 和 Chrome，测试服务在临时数据库生成虚构企业记录：

PYTHONPATH=app:app/tests STEPFUN_API_KEY='' ADMIN_TOKEN=test-only-token app/.venv/bin/python -m uvicorn ui_server:app --port 8767
# 另一终端；NODE_PATH 指向已安装 Playwright 的包目录

## 0.3 来源与引用修复

- URL 采集保存原始页面、正文、最终地址、采集时间。`source_captures` 保存采集与失败记录，`source_snapshots` 将来源快照绑定到 JD。
- 百度官方详情适配器核对官方主机、详情职位 ID、路由与 `detailData.recruitType`，从 `publishDate` 读取发布日期，并单独记录 `updateDate`。未知站点不套用百度规则。
- 来源事实仅由服务端从快照解析，客户端无法声明“已经核验”。部门缩写不决定企业；模型原始值、来源覆盖值分别记录。官方元信息变化会使检查缓存失效。
- 官方来源明确社招且没有阶段冲突时，直接归为范围外，不调用模型提取。阶段冲突进入待确认。
- 原文分为 S 编号片段。模型选择引用编号，程序还原原文、记录位置；不存在的编号和无依据引用仍被拦截。兼容旧单片段引用。
- 程序还原引用后，AI 仍须逐项判断引用是否支持能力要求、任务和岗位分类；编号正确不等于语义正确。
- 来源确实缺少信息时先补采集；模型输出问题最多修正一次。提取、修正、语义核验分别记录实际模型与耗时，供应商返回时记录 token 用量。
- 报告区分未提交、正在检查、待确认、范围外及岗位族样本不足；待确认页面显示岗位名称、公司、来源和失败原因，提供重新采集入口。

### 可选浏览器备用采集

HTTP 正文不足时只尝试一次浏览器采集，总时间最多 45 秒、并发 1；每个请求和重定向都须通过原有来源检查。没有有效正文就记录失败，不调用模型补写。

需要 Node.js、Playwright 和 Chrome。Codex 本地环境可使用现成运行库。其他环境可设置 `CAREERSAFARI_BROWSER_NODE`（Node 路径）、`CAREERSAFARI_BROWSER_NODE_PATH`（含 Playwright 的 node_modules 目录）。未配置该运行库时静态采集仍可用，动态页面明确返回采集失败。
